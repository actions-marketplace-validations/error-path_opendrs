# Why Bing has not crawled the opendrs site yet

Audit, 2026-10-21. Bing Webmaster Tools reports `https://error-path.github.io/opendrs/` as
"Discovered but not crawled", discovered on 2026-10-16, the day the site was registered.

## Verdict

Nothing on the site stops Bing from crawling it. Every page returns 200 to a bingbot user agent.
No page has `noindex`, no `X-Robots-Tag` header is sent, and canonical tags are correct. The
host's `robots.txt` returns 404, which crawlers read as "allow everything".

"Discovered but not crawled" five days after registration is Bing's normal queue for a new,
low-authority site. That is more likely on a shared `github.io` host with no root homepage and
almost no inbound links. Bing ranks its crawl queue by quality signals, and the site was sending
weak ones: 15 broken internal links, six internal implementation plans in the sitemap (one of them
663 KB) that shared a single boilerplate description, and no IndexNow. Those defects are now fixed
on the branch. Getting crawled from here depends on time, IndexNow and inbound links.

## Fixed on branch `docs/seo-crawlability`

1. **Internal plans removed from the site.** `superpowers` is now in `exclude:` next to `specs`,
   which is excluded for the same reason. Six large, internal pages with duplicate descriptions
   are no longer published or in the sitemap. No public page linked to them.
2. **Broken links fixed.** 13 were fixed in the source, and the other 2 were in the removed plans.
   Links into `bench/` and `skills/` now point to the GitHub blob URL, which works both on the site
   and when browsing the repo. The multi-line link to the field-test note in `experiments.md` is
   now on one line, so it is rewritten to `.html`.
3. **The review-heuristics research note** gets its own title (55 characters with the suffix) and
   description in place of the site-wide fallback.
4. **Homepage title and description shortened.** Title is 67 characters, down from 72. Description
   is 152 characters, down from 317, so Bing and Google show it in full.
5. **IndexNow.** The key file is `docs/7761d20ca5295159e2dd2f14ffccbe2b.txt`, served at
   `/opendrs/7761d20ca5295159e2dd2f14ffccbe2b.txt`. A key in a subdirectory may submit only URLs
   under that directory, which fits a project site. `.github/workflows/indexnow.yml` runs on
   `page_build`. After each successful Pages build it submits the published pages whose source
   changed. If `_config.yml` or the layout changed, it submits the whole sitemap. Running it by
   hand (`workflow_dispatch`) also submits the whole sitemap. It needs no secret, because an
   IndexNow key is public by design.

Checked with a local Jekyll 3.10 build using the same plugins as GitHub Pages. The sitemap has
20 URLs and no `superpowers/` pages. This report is not in it (`sitemap: false`). No internal link
in the 21 built pages is broken, every page has its own description, and the key file is
published with the key as its only content. The workflow's URL mapping was run against the live
sitemap, and the JSON payload was checked with `jq`. No submission was sent, because the key file
is not live yet.

## Not fixed (low value or outside the repo)

- **No `<lastmod>` in the sitemap.** jekyll-sitemap fills it only from front matter, and the legacy
  Pages build cannot run `jekyll-last-modified-at`. IndexNow tells Bing about changes directly,
  which covers the same need. Revisit only if the site moves to an Actions-built
  Pages deploy.
- **16 descriptions over 160 characters.** Search results truncate them. They do not block
  crawling. Shorten them over time, starting with the pages in the primary nav.
- **Liquid empties three GitHub Actions expressions** in the code examples in `auto-approve.md` and
  `github-action.md`. The live pages show `if: $`. This is a content bug, not an SEO one, so it is
  left for a separate fix.
- **Google Fonts stylesheet blocks rendering.** It is small, and changing it would touch the theme.

## Steps for you

Push the branch, merge it, and wait for the Pages build to finish (Actions tab → "pages build and
deployment" is green). Then work through these steps in order.

1. **Check that the key file is live.** Open
   `https://error-path.github.io/opendrs/7761d20ca5295159e2dd2f14ffccbe2b.txt`. It should show the
   key and nothing else.
2. **Run IndexNow once for every page.** GitHub → error-path/opendrs → Actions → **indexnow** (left
   list) → **Run workflow** → branch `main` → **Run workflow**. The log should end with
   `IndexNow HTTP 200` or `202`. A 403 means the key file is not live yet, so wait 10 minutes and
   run it again.
3. **Bing Webmaster Tools** (bing.com/webmasters, property `https://error-path.github.io/opendrs/`):
   - **Sitemaps** (left nav) → if `https://error-path.github.io/opendrs/sitemap.xml` is listed, open
     its ⋯ menu → **Resubmit**. If it is not listed, click **Submit sitemap** and paste that URL.
   - **URL Inspection** → paste `https://error-path.github.io/opendrs/` → **Inspect** →
     **Request indexing**. Do the same for `auto-approve.html`, `blast-radius.html` and
     `github-action.html`.
   - **URL Submission** (left nav) → paste the primary-nav URLs, one per line, up to the daily
     quota shown → **Submit**.
   - **IndexNow** (left nav) → a day after step 2, check that the submitted URLs are listed.
   - **Site Scan** (left nav) → **Start new scan** on `https://error-path.github.io/opendrs/` to confirm
     that no errors remain. Warnings about long descriptions are expected (see above).
4. **Google Search Console** (property `https://error-path.github.io/opendrs/`):
   - **Sitemaps** → the sitemap is already submitted. Google re-reads it on its own, so nothing is
     needed. The six removed plan URLs will drop out of **Pages → Not indexed** as "Not found
     (404)". That is expected and needs no action.
   - **URL inspection** → the homepage → **Request indexing**.
5. **Optional, recommended: create the root user site.** Create a public repo named exactly
   `error-path/error-path.github.io` and enable Pages on it. It needs two files:
   - `robots.txt`:
     ```
     User-agent: *
     Allow: /

     Sitemap: https://error-path.github.io/opendrs/sitemap.xml
     ```
   - `index.html`: a one-screen page with a title, one sentence about you or your projects, and a
     plain link to `https://error-path.github.io/opendrs/`.

   This gives the host a real homepage in place of a 404. It also gives a host-level `robots.txt`
   that points crawlers to the sitemap, and an internal link from the host root to the project.
   It cannot hurt, but it is not proven to be what unblocks Bing.
6. **Earn inbound links.** This is the main lever for a new site. Already planned: the
   awesome-claude-code submission (eligible from 2026-10-29), MCP directories, a Show HN or dev.to
   post, and setting `docs/assets/og.png` as the repo's social preview (repo Settings → General →
   Social preview). Links from the post bodies, not only the profile fields, are the ones that
   count.

## What to expect

- **IndexNow:** Bing usually fetches submitted URLs within one to three days. A crawl does not
  guarantee indexing.
- **Bing indexing:** for a new `github.io` project site, "Discovered but not crawled" often lasts
  two to six weeks. Seeing a crawl of the homepage within two weeks of steps 2 and 3 is on track.
  If URL Inspection still shows no crawl after four weeks, re-run Site Scan and look at
  **Crawl Information** for errors.
- **Google:** the homepage usually indexes within days to two weeks of a Request indexing. The
  deeper pages follow as Google re-crawls the sitemap.
- **Rankings** for "PR blast radius" and "auto-approve pull requests" depend mostly on inbound links.
  Expect them weeks after indexing, not days.
