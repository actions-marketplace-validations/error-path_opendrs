# Default weights: re-centring and saturation on ApacheJIT

Generated by `bench/apachejit/default-weights-experiment.ts`. Pooled over every project except `apache/hadoop`, on the dataset's official split. Row cache build `08355066ee67`; no new clones, no new signal replay — both candidates are pure transforms of the existing cached signals.

## Coverage

- 66653 row-cache commits considered (same coverage as the score-saturation experiment).
- Test-split base rate: 23.6% buggy.

## Candidates

- **V0 (current).** Unchanged `DEFAULT_WEIGHTS` (intercept -2.85).
- **V1 (intercept re-centred).** Intercept shifted by +1.016 (to -1.834), chosen so the **train**-split default-prior median score (0.307) lands at mid-yellow (0.55). Every signal value is unchanged; only the intercept moves. This is a monotonic transform of the logit, so it cannot change score ranking: calibrated AUC is identical to V0 by construction (confirmed below, not just asserted).
- **V2 (history/expertise scaled by repo age).** `history.churn`, `history.prior_fixes` and `expertise.author_commits` (the unbounded log1p-count signals; `history.incident`, a 0/1 flag, and `expertise.owner_ratio`, already a 0–1 ratio, are left as is — dividing a bounded value by a growing denominator does not match the diagnosis of raw, un-normalized *counts*) are each divided by `max(1, log1p(age in days since the project's earliest row-cache-resolved commit))`, computed per commit from the existing cached commit time and project, no new clone needed. A brand-new project's commits keep their raw value (divisor floored at 1); an old commit in a long-lived project has its raw count shrunk. This changes feature values, so it *can* change ranking and AUC — unlike V1.
- **V3.** V1 and V2 together.

## Decision (pre-registration's rule, applied per variant)

- **V1.** Red-share relative reduction -57.5% < 25% threshold; AUC-gain 95% CI 0.0000 to 0.0000 (includes 0 or positive — no significant loss) → by the letter of the rule: **reject**.
- **V2.** Red-share relative reduction -32.4% < 25% threshold; AUC-gain 95% CI -0.0058 to -0.0046 (entirely negative — significant loss) → by the letter of the rule: **reject**.
- **V3.** Red-share relative reduction -108.9% < 25% threshold; AUC-gain 95% CI -0.0058 to -0.0046 (entirely negative — significant loss) → by the letter of the rule: **reject**.

**But the literal rule is not the whole story for V1.** V1's AUC is unaffected by construction — it reshuffles no ranking at all — so it can satisfy the rule's AUC side no matter how large a shift is chosen, and a large enough intercept shift can always clear the red-share bar too, trivially, by moving the entire distribution down. The question that matters is whether tiers still mean anything afterward: see the buggy-rate-by-tier table above.

**Both candidates move saturation the wrong way, for two different reasons.**

- **V1's premise does not hold on ApacheJIT.** The pre-registration's rationale ("the median commit
  lands mid-yellow instead of near red") assumes today's median sits *above* mid-yellow, near red.
  On ApacheJIT it does not: the train-split default-prior median is 0.307, barely past the green/yellow
  boundary (0.3), nowhere near red (0.8). Moving it up to 0.55 therefore pushes a large share of the
  distribution that was sitting in green or low yellow into high yellow and red, which is exactly the
  "raises red share" result above, not a reduction. ApacheJIT's mature-but-moderate commits are, on
  average, already closer to green than to red under the current defaults; the saturation the
  pre-registration is chasing (black, vite: most PRs red) is a property of those specific repositories'
  histories, not of ApacheJIT's pooled distribution — see Caveats.
- **V2 backfires on sign, not magnitude.** `expertise.author_commits` carries a *negative* weight
  (−0.3, protective: more author experience lowers risk) of the same magnitude as `history.prior_fixes`
  (+0.3). Dividing all three scaled signals' raw values by the same per-commit age divisor shrinks every
  one of their contributions toward zero — but a mature project's author-commit counts (an experienced
  committer's log1p count) are typically larger in magnitude than its prior-fix/churn counts, so the
  *protective* contribution shrinks by more, in absolute logit, than the *risk* contributions do. Net
  effect: scores rise, not fall. A normalization that only targets raw counts without accounting for
  which of them are protective removes more safety margin than it removes inflated risk.

## Caveats

- **Repo-age anchor is the dataset's visible window, not true repo age.** `minTimeByProject` is the earliest row-cache-resolved commit per project (train starts 2003 for most projects), not the actual repository creation date; a project whose ApacheJIT-visible history starts later than its real first commit will have every commit's age understated, in the same direction for every variant.
- **V2 scopes the scaling to the unbounded count signals only** (`history.churn`, `history.prior_fixes`, `expertise.author_commits`), not `history.incident` (0/1) or `expertise.owner_ratio` (already 0–1): this is a reading of the pre-registration's "raw, un-normalized counts" diagnosis, not a change to the question.
- **V1's AUC-gain CI is reported for completeness, not because it could show a loss** — it is analytically identical to V0 (a monotonic rescoring), confirmed by the 0.0000 gain below.
- **No rename detection, no new history walk**: every signal value comes from the existing row cache exactly as `run.ts` computed it; only this script's own transforms (intercept shift, age-based division) are new.
- **One scaling sub-variant chosen, not both.** The pre-registration offered "divide by log1p(repo age in days) **or** log1p(total commits)" as alternatives ("at least one of"); this experiment implements only the repo-age version (dynamic per commit, needs no new clone or total-commit count). The repo-size alternative was not run.
- **No field-test repository rescoring.** The pre-registration allowed skipping this ("not a hard requirement... ApacheJIT alone still answers the question, descriptively weaker") when it is too slow for the bench budget. Both ApacheJIT results already reject decisively (saturation rises, not falls; V2/V3 also lose AUC), so the six field-test repos were not re-cloned and re-scored.
